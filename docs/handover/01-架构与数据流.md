# 接手文档 01 · 架构与数据流

> 本篇讲清楚：8 个 ROS 包各自干什么、有哪些节点、节点之间靠什么话题连起来、用了哪些坐标系。
> 配合 `02-逐包逐文件详解.md`（文件级）和 `03-控制器状态机详解.md`（控制器内部）一起看。

## 1. 8 个 ROS 包总览

`colcon list` 识别 8 个包。**编译有严格顺序**：`thermal_interfaces` 必须最先编，因为其它包要 import 它定义的消息。

| 包 | 类型 | 职责 | 含节点 |
|---|---|---|---|
| `thermal_interfaces` | ament_cmake | 自定义 msg/srv 定义 | 无（只是接口） |
| `g1_description` | ament_cmake | 机器人 URDF + G1 mesh 资产 | 无（被 launch 读取） |
| `thermal_sensor_sim` | ament_python | 热相机仿真、RGB 着色 | `sensor_node`, `colorizer_node` |
| `signal_preprocessor` | ament_python | 热图像时序+空间滤波 | `preprocessor_node` |
| `thermal_field_reconstructor` | ament_python | 热场重建、世界热图融合、可见性、残差 | `reconstructor_node`, `thermal_mapper_node` |
| `thermal_gradient_processor` | ament_python | Sobel/中心差分梯度 | `gradient_node` |
| `thermal_motion_controller` | ament_python | 源跟踪、决策控制器、规划、清场 | `source_tracker_node`, `controller_node` |
| `thermal_bringup` | ament_cmake | launch + 配置 + world + RViz | 无（编排其它一切） |

> ament_cmake = 用 CMake 构建（C++ 风格，接口包和纯资源包用）；ament_python = 纯 Python 包。

## 2. 运行时节点清单

一次完整 `sim_nav_slam_launch.py` 启动后，`ros2 node list` 大致能看到：

**仿真/导航基础设施（来自 ROS 官方包）：**
- `/robot_state_publisher` — 读 URDF，发布机器人各 link 的静态 TF
- Gazebo 进程（gzserver，含 diff_drive 插件发 `/odom`，ray 插件发 `/scan`）
- `/slam_toolbox` — SLAM 建图
- `/controller_server` `/planner_server` `/bt_navigator` `/smoother_server` `/behavior_server` `/waypoint_follower` `/velocity_smoother` `/lifecycle_manager_nav` — Nav2 全家桶
- `/rviz2`（`use_rviz:=true` 时）

**本项目热导航管线（8 个自研节点中除接口外的 7 个会跑）：**
- `/sensor_node` — 热相机仿真
- `/colorizer_node` — 热图像着色（仅给 RViz 看）
- `/preprocessor_node` — 滤波
- `/reconstructor_node` — 热场重建 + 提供 service
- `/thermal_mapper_node` — 世界热图融合
- `/gradient_node` — 梯度
- `/source_tracker_node` — 源跟踪
- `/controller_node` — 决策大脑

## 3. 完整数据流（核心）

### 3.1 热相机感知链（决策的“眼睛”）

```
sensor_node
  └─ /sim/thermal_raw  (sensor_msgs/Image, 32FC1, 64×48, 10Hz, BEST_EFFORT)
        ├──► colorizer_node ─► /sim/thermal_colorized (rgb8, 给 RViz 显示)
        ├──► preprocessor_node
        │       └─ /thermal/filtered (Image 32FC1, 10Hz)
        │             ├──► reconstructor_node
        │             │       ├─ /thermal/field (ThermalField, 10Hz, 含 hotspots)
        │             │       └─ service /thermal/get_field_info
        │             │             └──► gradient_node
        │             │                     └─ /thermal/gradient (GradientArray, 10Hz)
        │             └──► thermal_mapper_node  ← 也订阅 /odom 和 /map(SLAM)
        │                     └─ /thermal/map (ThermalMap, 5Hz, 世界坐标系大网格)
        │                           └──► source_tracker_node
        │                                   └─ /thermal/sources (SourceEstimateArray, 5Hz)
  └─ /sim/thermal_sources_truth (SourceEstimateArray, 10Hz)  ← ★只给评测/采集脚本，控制器不订阅★
```

注意几个关键点：
- `preprocessor` 的输出 `/thermal/filtered` 同时喂给 **reconstructor**（→梯度链）和 **thermal_mapper**（→世界热图链）。这是两条平行的感知路径。
- `thermal_mapper` 还要订阅 `/odom`（机器人在哪）和 `/map`（SLAM 占据栅格，用于可见性射线检测）。
- `/sim/thermal_sources_truth` 是“上帝视角”真值，**只有评测才能用**。

### 3.2 SLAM + Nav2 导航链（机器人的“腿”）

```
Gazebo diff_drive 插件 ─► /odom (nav_msgs/Odometry, ~20Hz)
Gazebo ray 插件        ─► /scan (sensor_msgs/LaserScan, 10Hz)
        │
        ▼
slam_toolbox ─► /map (nav_msgs/OccupancyGrid) + TF(map→odom)
        │
        ▼
Nav2 (controller_server/planner_server/bt_navigator/...)
        ▲
        │ navigate_to_pose 动作（controller_node 作为 ActionClient 发目标）
controller_node
        └─ /cmd_vel (geometry_msgs/Twist, ~10Hz)  ─► Gazebo（最终驱动机器人）
```

### 3.3 决策闭环（controller_node 的输入输出）

```
controller_node 订阅:
  /thermal/gradient   (GradientArray)  ← 近距离梯度上升信号
  /thermal/map        (ThermalMap)     ← 全局探索的世界热图
  /thermal/sources    (SourceEstimateArray) ← 候选/确认源
  /odom               (Odometry)       ← 位置/朝向
  /map                (OccupancyGrid)  ← 可达性/可见性检查
  TF(map→base_link)                    ← Nav2 目标的坐标转换

controller_node 发布:
  /cmd_vel            (Twist)          ← 速度指令（FINE 直发 / COARSE 兜底）
  /thermal/clearance  (Float32)        ← 清场概率（仅 residual 策略下评估）
  navigate_to_pose 动作目标             ← 交给 Nav2（COARSE 优先）
```

## 4. 话题/服务/动作总表

| 名称 | 类型 | 发布者 | 订阅者 | 频率/QoS |
|---|---|---|---|---|
| `/sim/thermal_raw` | sensor_msgs/Image (32FC1) | sensor_node | colorizer, preprocessor | 10Hz / BEST_EFFORT |
| `/sim/thermal_colorized` | sensor_msgs/Image (rgb8) | colorizer_node | RViz | 10Hz / BEST_EFFORT |
| `/sim/thermal_sources_truth` | thermal_interfaces/SourceEstimateArray | sensor_node | **仅采集/评测** | 10Hz / BEST_EFFORT |
| `/thermal/filtered` | sensor_msgs/Image (32FC1) | preprocessor_node | reconstructor, thermal_mapper | 10Hz / BEST_EFFORT |
| `/thermal/field` | thermal_interfaces/ThermalField | reconstructor_node | gradient_node | 10Hz / RELIABLE |
| `/thermal/map` | thermal_interfaces/ThermalMap | thermal_mapper_node | source_tracker, controller | 5Hz / RELIABLE |
| `/thermal/sources` | thermal_interfaces/SourceEstimateArray | source_tracker_node | controller | 5Hz / RELIABLE |
| `/thermal/gradient` | thermal_interfaces/GradientArray | gradient_node | controller | 10Hz / RELIABLE |
| `/thermal/clearance` | std_msgs/Float32 | controller_node | 采集脚本 | 按需 |
| `/thermal/get_field_info` | thermal_interfaces/srv/GetFieldInfo | reconstructor_node | 手动查询 | service |
| `/cmd_vel` | geometry_msgs/Twist | controller / Nav2 | Gazebo | ~10Hz |
| `/odom` | nav_msgs/Odometry | Gazebo diff_drive | mapper, controller, sensor, slam | ~20Hz |
| `/scan` | sensor_msgs/LaserScan | Gazebo ray | slam, Nav2 | 10Hz |
| `/map` | nav_msgs/OccupancyGrid | slam_toolbox | Nav2, mapper, controller | ~0.2Hz / TRANSIENT_LOCAL |
| `/plan` | nav_msgs/Path | Nav2 planner | 采集脚本 | 按需 |
| `navigate_to_pose` | nav2_msgs/action/NavigateToPose | (server) Nav2 / (client) controller | — | action |

> **QoS 小贴士**：sensor 类高频图像用 BEST_EFFORT（丢帧无所谓），结构化结果（field/map/sources/gradient）用 RELIABLE。`/map` 用 TRANSIENT_LOCAL（晚订阅也能拿到最后一帧）。订阅端 QoS 不匹配会静默收不到——排错时第一个怀疑点。

## 5. 自定义消息（thermal_interfaces）

源文件在 `thermal_interfaces/msg/` 和 `srv/`。逐个说明：

- **`ThermalPoint.msg`** — 图像里一个热点：像素坐标 `pixel_x/y`、世界坐标 `world_position`、温度、强度、置信度。
- **`ThermalField.msg`** — 一帧重建热场：`width/height`、分辨率、原点、`data[]`（展平的温度数组）、min/max/mean/std 温度、`hotspots[]`（ThermalPoint 数组）、重建方法。**注意**：它的坐标分辨率（0.01）是“像素级”的，不是世界坐标——它本质是“整理过的图像 + 统计”。
- **`Gradient.msg`** — 单像素梯度向量：grad_x/y、magnitude、direction_rad、temperature。
- **`GradientArray.msg`** — 梯度数组 + 全局信息：`max_magnitude`、`peak_pixel_x/y`（最热像素）、`peak_temperature_celsius`（视野内最高温，v2 修过——以前报的是“最大梯度像素”的温度，导致在离源 3~4m 处就误判“找到了”）、method。
- **`ThermalMap.msg`** — ★世界坐标系热图★：`width/height/resolution/origin_x/y`，外加每格的 `temperature_mean[]`、`temperature_variance[]`、`confidence[]`、`visit_count[]`、`last_seen_age_s[]`、`view_state[]`（0=没看过/1=被挡/2=看清）、`view_sectors[]`（被从哪些方位扇区看过的位掩码）。frame 是 `world`。这是 phase0/phase1 的核心数据结构。
- **`SourceEstimate.msg`** — 一个源估计：`id`、`status`（candidate/confirmed/stale/suppressed/truth_active/truth_inactive）、`position`、协方差、强度、sigma、存在概率、置信度、观测次数。
- **`SourceEstimateArray.msg`** — 源估计数组。同时被 source_tracker（真实估计）和 sensor_node（真值，status 带 `truth_` 前缀）复用。
- **`GetFieldInfo.srv`** — 请求 `include_full_data`，返回当前热场统计摘要 + 热点温度列表。

## 6. 坐标系（frame）与一个容易踩的坑

涉及 4 个坐标系：

```
map ──(slam_toolbox 发布)──► odom ──(diff_drive 发布)──► base_link ──► thermal_camera / lidar_link
```

- **`world`（逻辑世界系）**：本项目额外定义的“真实世界坐标”。机器人出生点 `spawn=(-6, 0)`。
  **world = spawn + odom**（即 odom 坐标 + 出生偏移）。热源真值、世界热图都在这个系里。
- **`odom`**：里程计积分系，机器人启动处为原点 (0,0)。会漂移。
- **`map`**：SLAM 修正后的全局系。
- **`base_link`**：机器人本体。

**关键设计决策（v31 FIX-1）**：因为仿真热相机图像是按 **Gazebo/odom 位姿**渲染的，所以世界热图和控制器**默认用 odom 对齐的世界系**（`pose_source=odom`），即 `world = spawn + odom`。这样热图和相机物理上对齐。但给 **Nav2 发目标时**仍要转成 `map` 系——用实时 TF（`map→base_link`）换算。

这就是 controller 里 `_update_world_pos_from_tf()` 和 `_send_nav2_goal()` 那段坐标变换的由来。新手看到“为什么又是 odom 又是 map 又是 spawn 偏移”不要慌，记住：
- **算热的一切**（热图/源/梯度决策）：用 `world = spawn + odom`。
- **发 Nav2 目标**：转成 `map` 系。
- `thermal_mapper_node` 把 SLAM `/map` 的原点也加了 `spawn` 偏移（`_slam_map_cb`），让占据栅格和世界热图对齐。

> 占据栅格几何常数（中心 `(-6,0)`、尺寸 `50m`）统一在 `thermal_field_reconstructor/grid_geometry.py`，离线真值栅格（`world_occupancy.py`）和在线世界热图共用，避免两套坐标静默漂移。

## 7. 启动时序（launch 里写死的定时）

`sim_nav_slam_launch.py` 用 `TimerAction` 错峰启动，避免依赖还没起来就连：

```
t=0s   gzserver + robot_state_publisher
t=5s   gzclient（use_gzclient:=true 时的 Gazebo 图形界面）
t=6s   spawn 机器人 @ (-6, 0, 0.141)
t=9s   slam_toolbox
t=12s  Nav2 全套 + lifecycle_manager（autostart）
t=18s  热管线 7 节点（sensor/preprocessor/reconstructor/mapper/gradient/source_tracker/controller）
t=20s  colorizer + RViz
```

所以：RViz 大约启动 20 秒后才出现；数据采集要等 ~25-30 秒管线稳定后再开。

## 8. launch 参数

`ros2 launch thermal_bringup sim_nav_slam_launch.py --show-args`：

| 参数 | 默认 | 作用 |
|---|---|---|
| `use_rviz` | true | 是否开 RViz |
| `use_gzclient` | true | 是否开 Gazebo 图形界面 |
| `use_sim_time` | **false** | 时间源。当前用墙钟，**不要随便改**（见 `06` 已知问题） |
| `world_file` | thermal_scene_nav.world | Gazebo 世界（几何/障碍） |
| `scenario_file` | ''（空→Config-B 内置） | 热源布局/动态（YAML） |
| `run_seed` | 0 | 随机种子（传给 sensor 噪声 + 控制器） |
| `strategy` | full | 控制器策略：full/frontier/levy/residual（基线挂架，见 `04`） |
| `scenario_jitter_std_m` | 0.0 | 给源位置加高斯扰动（多 seed 用） |

**world 和 scenario 是两个正交的测试轴**：world 决定几何障碍，scenario 决定热源怎么放/怎么动。可任意组合（见 `04` 评测矩阵）。
